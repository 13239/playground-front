# 친구·알림 동작 개선

검증일: 2026-10-28

## 사용자에게 달라지는 동작

- 헤더에서 친구·알림 팝업을 열거나 닫아도 홈의 친구·대화 탭 선택이 유지된다. 팝업의 탭을 바꿔도 홈의 선택은 바뀌지 않는다.
- 친구 수락 알림은 친구 목록으로 연결한다. 1:1 대화는 사용자가 대화 버튼을 누를 때 생성한다.
- 상단 안내의 확인 버튼은 알림 안내라면 해당 요청·목록으로 이동하고 일반 안내라면 닫는다(2026-10-30 변경). 모바일 모달이 열렸을 때도 확인 버튼을 누를 수 있다.
- 알림창을 열면 확인한 알림 경계까지 자동으로 읽음 처리한다. 서버 반영에 성공하면 배지와 목록의 안 읽음 표시를 함께 갱신한다.
- 알림창을 보고 있는 동안 새 알림이 오면 새로운 경계까지 이어서 읽는다. 숨은 브라우저 탭은 실제 문서로 돌아올 때 처리한다.

## 원인과 함께 수정한 문제

- 홈 탭과 전역 팝업이 하나의 표시 위치를 사용해 팝업을 열면 홈이 전체 탭으로 돌아갔다. 홈 선택을 별도 상태로 분리했다.
- 알림 읽기 후 대화 요약·이력을 불필요하게 조회했고, 연속 조회가 공용 채팅과 공유하는 사용자 조회 예산을 소진할 수 있었다. 읽음 명령에서 불필요한 채팅 조회를 제거하고 나머지 조회는 같은 종류를 합쳐 600ms 이상의 간격으로 전송한다.
- 조회 제한 응답에 서버의 대기 시간과 대상 방·페이지가 없었다. 채팅 서버가 이 정보를 제공하며 클라이언트는 해당 조회만 최대 두 번 재시도한다. 메시지 전송은 자동 재전송하지 않는다.
- 이미 읽은 알림을 다시 처리할 때도 실시간 변경을 방송했다. 백엔드는 실제로 읽음 상태가 바뀐 경우에만 다른 탭으로 변경을 전달한다. 읽음 경계의 소유자 검증은 유지한다.
- 이전 방·페이지의 이력과 오류가 새 화면에 반영될 수 있었다. 현재 요청 대상과 응답을 비교하고 닫힌 화면의 조회를 취소한다.
- 목록 갱신이 대화 이력의 로딩을 끝내거나, 다시 확인 버튼이 실제 대화 조회를 복구하지 못할 수 있었다. 두 흐름을 분리하고 재확인 시 활성 대화를 다시 연다.
- 닫기·탭 이동·로그인 변경 전에 요청한 프로필이 늦게 도착해 카드를 다시 표시할 수 있었다. 해제 이후 응답을 무시한다.

## 검증 결과

- 프론트 TypeScript 검사, 변경 파일 ESLint 검사, Next.js 16.4.2 프로덕션 빌드 통과.
- 백엔드와 채팅 서버 Java 컴파일 통과.
- 저장소 상태·알림 경합·조회 재시도·늦은 응답 관련 임시 회귀 테스트 20개 통과.
- 백엔드 알림 읽음의 중복 방송 방지 테스트 5개 통과.
- 채팅 서버 오류 응답의 대기 시간·방·페이지·오류 코드 테스트 2개 통과.
- 원본 컴포넌트·CSS를 사용한 독립 검증 화면에서 Chromium과 Microsoft Edge의 탭 유지, 안내 닫기, 자동 읽음, 친구 수락 알림 이동, Escape 닫기를 확인했다.
- 두 브라우저 모두 320·390·768·1920·2560·3840·5120px에서 팝업과 페이지의 가로 넘침이 없으며, 모바일 모달 안의 안내 확인 버튼도 동작했다.
- 검증에 사용한 임시 테스트 소스와 브라우저 검증 화면은 실행 후 삭제했다. 기존 테스트는 유지했다.

브라우저 검증은 모의 API·WebSocket 연결을 사용했다. 실제 로그인 계정과 MySQL·Redis·MongoDB·Kafka를 함께 사용하는 통합 검증, Firefox·Safari 검증 및 운영 배포는 수행하지 않았다. 적용 범위는 프론트·백엔드·채팅 서버 세 프로젝트이며 DB 스키마 변경은 없다.

## 2026-10-30 추가 개선

- 친구 요청 실시간 안내는 원본 알림을 보관한다. 확인 버튼을 누르면 기존 읽음 처리와 요청 위치 조회를 재사용해 수락·거절 버튼이 있는 받은 요청의 실제 페이지로 이동하고 해당 행을 강조한다. 일반 안내는 계속 닫기만 한다.
- 접속자 목록의 아바타·닉네임 행은 기존 공통 미니 프로필을 연다. 채팅 서버는 인증 서버의 최신 공개 프로필에서 공개 UUID·닉네임·아바타를 조회하며 내부 회원 번호를 응답에 포함하지 않는다. 본인·이미 친구·보낸 요청·받은 요청·차단 상태는 기존 미니 프로필 규칙을 따른다.
- 미니 프로필은 portal 안에서 조작하는 동안 원래 접속자 행을 유지한다. 모바일 전체 채팅 dialog에서도 프로필을 조작할 수 있고 요청 확인으로 이동할 때 원래 modal을 닫는다. 친구 추가 실패 이유는 미니 프로필 안에도 표시한다.
- 알림 팝업은 데스크톱의 바깥 영역과 모바일 backdrop을 누르면 닫힌다. 내부 클릭은 유지하고 헤더 버튼의 열기·닫기 동작과 Escape 닫기도 유지한다.

### 친구 요청 제한

이전에는 알림 읽음·방 조회·친구 변경이 회원별 공용 60회/분 카운터를 사용했다. 새 정책은 기능별 Redis 키로 예산을 분리하고 원자적 공통 Lua의 남은 만료 시간을 `Retry-After`로 전달한다. 기존 공용 카운터가 새 정책을 차단하지 않도록 새 키 공간을 사용한다.

| 요청 종류 | 예산 |
| --- | --- |
| 친구 요청 API 호출·중복 확인 | 회원별 120회/분 |
| 실제 새 친구 요청 전송 | 회원별 60회/분, 기존 50회/24시간 정책도 적용 |
| 알림 읽음 | 회원별 120회/분 |
| 방 상세 조회 | 회원별 120회/분 |
| 나머지 관계·그룹 변경 | 회원별 60회/분 |

이미 대기 중인 요청·친구 관계를 확인하는 호출은 새 전송 횟수를 소비하거나 알림을 중복 생성하지 않는다. 반복 호출 자체의 서버 보호 제한은 유지한다. 거절당한 발신자의 재요청 보호는 아래의 연속 5회 거절 정책으로 추가 변경했다. 친구 200명 한도, 상대의 받은 요청 200개 한도는 유지하고 각각의 구체적인 오류로 안내한다. 기존에는 거절했던 수신자가 반대 방향으로 먼저 요청해도 같은 보호 시간에 막혔지만, 이 경우는 명시적인 요청 의사이므로 허용한다. 거절 후 재요청 보호와 인원 한도는 409로 구분하며 실제 요청 폭주·24시간 전송 한도는 429를 사용한다.

### 접속자 목록 여백 보정

프로필 버튼 도입 후 늘어난 행의 최소 높이를 2.75rem에서 2rem으로 줄이고 상하 패딩을 0.1em으로 조정했다. 공통 프로필 버튼에서 상속하던 가로 가운데 정렬도 목록 범위에서 왼쪽 정렬로 바꿨다. 아바타·글자 크기와 미니 프로필 동작은 유지한다.

원본 전역·소셜·로비 CSS를 적용한 독립 목록에서 Chrome 156.0.8078.48과 Edge 156.0.4314.50을 배율 100%로 검증했다. 위 추가 검증과 같은 10개 CSS viewport에서 화면 경계·가로 넘침·왼쪽 정렬을 확인했다. 행 높이는 FHD 이하 32px, QHD 36px, 4K 44px, 5K 48px으로 공통 글꼴 배율을 따랐다. Firefox·Safari는 미검증이며 이번 변경은 CSS만 수정했다.

### 연속 5회 거절 후 24시간 제한

2026-10-30 사용자 요청에 따라 한 번 거절되면 제한하던 정책을 변경했다.

- 같은 발신자→상대 방향의 실제 거절만 누적한다. 1~4회 거절 후에는 즉시 다시 요청할 수 있고 5회째 거절 시점부터 해당 상대에게 24시간 동안 재요청할 수 없다.
- 수락하면 양쪽의 연속 거절 기록을 초기화한다. 24시간 제한이 끝난 뒤 첫 재요청도 새 기록으로 시작한다.
- 취소는 거절 횟수를 늘리지 않고 기존 누적 횟수도 지우지 않는다. 같은 거절의 재전송·동시 처리는 한 번만 반영한다.
- 다른 상대와 반대 방향의 요청은 별도 기록을 사용한다. 친구 요청·관계 변경·차단은 기존 회원 잠금 순서와 트랜잭션을 공유한다.
- 제한 사유는 서버와 프론트 모두 연속 5회 및 마지막 거절 후 24시간 기준으로 안내한다.

새 Flyway 마이그레이션 `V35__track_consecutive_friend_request_rejections.sql`은 방향별 횟수와 제한 만료 시각을 MySQL에 보존하는 테이블을 추가한다. 기존 REJECTED 관계는 확인 가능한 마지막 거절 1회로 이관하고 즉시 재요청을 허용한다. 과거 전체 거절 이력이 없으므로 이전 횟수를 추정해 제한하지 않는다. 이번 정책은 앞선 UI 수정과 달리 DB 마이그레이션이 필요하며, 백엔드 재시작 시 V35가 적용되어야 한다. 기존 버전 마이그레이션은 수정하지 않았다([Flyway 공식 문서](https://documentation.red-gate.com/flyway/flyway-concepts/migrations/versioned-migrations)).

실제 사용자 DB와 분리한 임시 MySQL 8.0.37에서 V29 기반 스키마와 V35 Flyway 마이그레이션을 실행했다. 실제 저장소·SQL·트랜잭션·서비스를 연결하고 Redis 예산과 후속 실시간 방송은 모의 처리한 통합 테스트 12개가 통과했다. 기존 거절 이관, 1~5회 누적, 24시간 직전·정확한 만료 경계, 수락 초기화, 취소, 중복·동시 거절, 상대·방향 분리, 서비스 재생성 후 제한 유지, 본인 요청 거절 방지, 트랜잭션 실패 시 상태·누적·기한의 동시 롤백을 확인했다. 백엔드 컴파일과 프론트 TypeScript·변경 파일 ESLint 검사도 통과했다. 새 검증용 테스트 코드와 임시 MySQL 인스턴스·데이터는 검증 후 삭제했다. 검증 기록은 프로젝트 루트의 `artifacts/friend-rejection-policy-2026-10-30/`에 보존한다. 실제 로그인·전체 서비스 실시간 연결 및 브라우저 화면 검증은 이번 정책 변경에서 재실행하지 않았다.

### 본인 우선 표시와 접속자 무한 스크롤

- 현재 접속자는 인증된 본인을 첫 항목에 한 번 표시하고 닉네임 옆에 `(나)`를 붙인다. 닉네임이 같아도 연결의 검증된 회원 번호로 판별하며 공개 응답에는 본인 여부와 기존 공개 UUID만 전달한다.
- 본인이 기본 조회 범위보다 뒤에 있어도 Redis의 유효한 리스를 확인해 첫 조회에 포함한다. 이후 이어 읽기에서는 본인을 제외해 누락·중복 없이 나머지 접속자를 읽는다. 내부 조회 경계는 기존 연결 전용 무작위 토큰으로만 공개한다.
- 사용자 지정 예외에 따라 이 목록에는 번호 페이지·더 보기 버튼을 두지 않고 내부 스크롤의 끝이 가까워질 때 다음 50명 묶음을 자동으로 조회한다. 기존 접속자 행 높이·미니 프로필 버튼은 유지한다.
- 대기 중인 조회는 한 건만 유지하고 1.2초 간격과 서버의 대기 시간을 따른다. 목록을 닫거나 연결·세션이 바뀌면 대기 조회와 늦은 응답을 해제한다. 실패 시 자동 반복을 멈추고 기존 새로고침 버튼으로 복구한다.

검증은 다음과 같이 수행했다.

- 채팅 서버 Java 컴파일 및 임시 회귀 테스트 3개 통과: 본인 우선 정렬, 동명이인 판별, 이어 읽기 경계와 본인 중복 방지.
- 실제 Redis에 별도 임시 키로 원본 Lua를 실행한 8개 검증 통과: 본인이 기본 범위 밖에 있는 115명 목록, 조회 크기 1·100, 본인만 접속, 만료·없는 본인 리스, 빈 목록, 256개 검사 상한을 넘는 만료 항목의 이어 읽기. 검증 키는 실행 후 삭제했다. 기존 BYLEX 방식과 고정 검사 상한은 유지했다([Redis ZRANGE 공식 문서](https://redis.io/docs/latest/commands/zrange/)).
- 원본 프론트 상태 저장소의 조회 간격·중복 진입 방지·늦은 응답 무시·서버 대기 연장·시간 초과 후 중단·새로고침 복구·연결 종료 시 취소·본인 여부 프로토콜 검증을 확인했다.
- 원본 컴포넌트·CSS·상태 저장소를 사용하는 모의 인증·소켓 환경에서 Chrome 156.0.8078.48, Edge 156.0.4314.50, 배율 100%로 50→100→115명 무한 스크롤, 본인 첫 항목·단일 표시, 프로필 버튼, 실패 후 자동 중단·새로고침, 닫힘 시 대기 조회 취소를 확인했다.
- 두 브라우저에서 320×568, 390×844, 844×390, 768×1024, 1024×768, 1280×720, 1920×1080, 2560×1440, 3840×2160, 5120×2880으로 같은 페이지 크기를 순차 변경하면서 본인 표시·팝업 경계·가로 넘침을 확인했다.
- Next.js 16.4.2 프로덕션 빌드, TypeScript 검사, 변경 파일 ESLint 검사 통과. 새 테스트 소스는 검증 후 삭제하고 기록·화면은 프로젝트 루트의 `artifacts/presence-self-infinite-2026-10-30/`에 보존했다.

실제 로그인 계정으로 전체 서비스를 연결한 통합 동작과 Firefox·Safari는 미검증이다. 이번 접속자 변경은 프론트와 채팅 서버에 적용하며 채팅 서버 재시작이 필요하다. 추가 DB 마이그레이션은 없다.
