# 페이지 크기와 반응형·브라우저 호환성 공통 기준

2026-10-28 사용자가 확정한 아래 7절·8절은 오목에 한정하지 않고 기존·신규 모든 프론트엔드 화면에 적용한다. AI는 화면 개발·수정 전 이 규칙을 읽고 구현 및 검증에 반영한다. 현재 구현 수치와 화면별 설명은 아래 규칙의 가독성·조작성 우선 원칙 안에서 해석하며 고정된 설계 목표로 삼지 않는다.

## 7. 프론트엔드 반응형 UI 및 해상도별 화면 최적화 규칙

모든 프론트엔드 화면은 **FHD(1920×1080)를 기본 설계 기준**으로 하며, QHD(2560×1440), 4K(3840×2160), 5K(5120×2880), 모바일, 태블릿 등 다양한 화면 크기와 해상도에서 최적화된 UI를 제공해야 한다.

### 7.1. FHD 기준 화면 구성

- FHD(1920×1080) 환경에서는 가능한 한 페이지 스크롤 없이 주요 콘텐츠와 UI 요소가 한 화면에 모두 표시되도록 설계한다.
- 콘텐츠의 양이나 화면 구조상 한 화면에 모든 요소를 표시하기 어려운 경우에는 스크롤을 허용한다.
- 스크롤을 없애기 위해 텍스트나 UI 요소를 과도하게 축소해서는 안 된다.
- 실제 브라우저의 콘텐츠 표시 영역(viewport)을 기준으로 레이아웃을 계산해야 한다.

### 7.2. 고해상도(QHD, 4K, 5K) 화면 대응

- 해상도가 높아지면 화면 크기에 맞춰 레이아웃, 콘텐츠 영역, 여백 및 UI 요소의 크기가 자연스럽게 커지도록 구현한다.
- FHD에서 사용한 UI 크기를 모든 해상도에 고정하지 않는다.
- 반대로 해상도 증가 비율만큼 모든 요소를 단순 확대해서도 안 된다.
- 글꼴, 버튼, 아이콘, 입력창, 카드, 테이블 등은 화면 크기에 맞춰 적절하게 조절하되, 지나치게 확대되어 보이지 않도록 한다.
- 고해상도의 넓은 화면 공간을 효율적으로 활용하면서도 요소 간 비율, 시각적 균형, 가독성을 유지해야 한다.
- 필요에 따라 요소별 최대 크기(max-size)를 설정하여 과도한 확대를 방지한다.

### 7.3. 브라우저 창 크기 변경 대응

- 브라우저 창의 가로 또는 세로 크기를 변경하면 내부 레이아웃과 UI 요소도 사용 가능한 화면 영역에 맞춰 자연스럽게 조정되어야 한다.
- 화면 크기가 작아질 때는 콘텐츠 영역, 여백, 요소 크기 등을 적절하게 축소하거나 재배치한다.
- 단, 모든 요소를 화면 크기에 비례하여 무조건 축소해서는 안 된다.
- 텍스트, 버튼, 입력창 등 가독성과 조작성이 중요한 요소에는 최소 크기(min-size)를 적용하여 지나치게 작아지지 않도록 한다.
- 특정 요소는 화면이 작아지더라도 기존 크기를 유지해야 할 수 있으며, 이러한 경우 요소의 특성과 사용성을 우선하여 크기를 유지한다.
- 최소 크기에 도달한 이후에는 추가 축소 대신 줄바꿈, 열 재배치, 콘텐츠 영역 조정 또는 필요한 부분에 한정한 스크롤 등을 적용한다.
- 브라우저 크기 변경 시 요소가 겹치거나 잘리거나 레이아웃이 깨지는 현상이 발생해서는 안 된다.

### 7.4. 모바일 및 태블릿 대응

- 모바일과 태블릿에서는 기기의 화면 크기 및 방향(세로/가로)에 맞는 반응형 레이아웃을 제공한다.
- 데스크톱 화면을 단순히 축소하는 방식이 아니라, 기기 특성에 맞춰 요소 배치와 크기를 최적화한다.
- 좁은 화면에서는 필요에 따라 다단 레이아웃을 단일 열로 변경하거나 요소를 재배치한다.
- 텍스트 가독성, 터치 영역, 버튼 크기 및 요소 간 간격을 충분히 확보한다.
- 화면 너비를 초과하거나 요소가 겹치는 현상을 방지한다.
- 모바일 및 태블릿에서 필요한 세로 스크롤은 허용하되, 불필요한 가로 스크롤은 발생하지 않도록 한다.

### 7.5. UI 요소 크기 조절 원칙

- UI 요소의 크기는 화면 크기에 따라 유연하게 조절하되, 요소별 최소 크기와 최대 크기를 고려해야 한다.
- 모든 요소에 동일한 확대·축소 비율을 일괄 적용하지 않는다.
- 각 요소의 용도와 특성에 따라 고정 크기, 유동 크기, 최소·최대 크기 제한 등을 적절히 조합한다.
- CSS의 `clamp()`, `min()`, `max()`, `%`, `rem`, `vw`, `vh`, Flexbox, Grid, Media Query, Container Query 등을 상황에 맞게 활용한다.
- 특정 해상도에서만 정상적으로 보이도록 고정된 픽셀 값에 과도하게 의존하지 않는다.
- 화면 크기 변화에 따른 레이아웃의 연속성, 가독성, 사용성 및 시각적 일관성을 유지한다.

### 7.6. 반응형 처리 우선순위

화면 크기가 변할 때는 다음 원칙을 우선 적용한다.

1. 콘텐츠의 가독성과 UI 조작성을 유지한다.
2. 사용 가능한 화면 공간에 맞춰 레이아웃과 요소 배치를 조정한다.
3. 필요한 요소는 최소·최대 크기 범위 내에서 자연스럽게 확대하거나 축소한다.
4. 최소 크기 이하로 축소해야 하는 상황에서는 요소 크기를 유지하고 레이아웃을 재구성한다.
5. 레이아웃 재구성만으로 해결할 수 없다면 필요한 영역에 스크롤을 허용한다.
6. 스크롤 방지를 목적으로 가독성이나 사용성을 희생하지 않는다.

## 8. 브라우저 간 UI 일관성 및 호환성 규칙

모든 프론트엔드 화면은 Chrome, Edge, Firefox, Safari 등 주요 최신 브라우저에서 최대한 동일한 레이아웃과 시각적 결과를 제공하도록 개발해야 한다.

### 8.1. 브라우저별 화면 일관성

- 동일한 뷰포트 크기에서 브라우저 종류에 따라 요소의 크기, 위치, 간격, 정렬 및 레이아웃이 달라지지 않도록 구현한다.
- 브라우저별 기본 스타일 차이로 인해 UI가 다르게 보이지 않도록 CSS Reset 또는 Normalize 등의 방식을 적용한다.
- 폰트, 버튼, 입력창, 셀렉트 박스 등 브라우저 기본 렌더링 차이가 발생할 수 있는 요소는 일관된 스타일을 적용한다.
- 브라우저별 폰트 렌더링 등 불가피한 미세한 차이는 허용하되, 사용자가 인지할 수 있는 레이아웃 차이와 기능상 문제는 최소화한다.

### 8.2. 반응형 동작 일관성

- 브라우저 종류와 관계없이 동일한 화면 크기에서 동일한 반응형 규칙이 적용되어야 한다.
- 브라우저 창 크기를 변경했을 때 요소의 확대·축소, 재배치, 최소·최대 크기 제한이 일관되게 동작해야 한다.
- 특정 브라우저에서만 요소가 겹치거나 잘리거나 불필요한 스크롤이 발생해서는 안 된다.
- 브라우저별 CSS 및 기능 지원 여부를 고려하여 호환 가능한 구현 방식을 사용한다.

### 8.3. 검증 기준

- FHD, QHD, 4K, 5K 및 주요 모바일·태블릿 화면 크기에서 레이아웃을 검증한다.
- 브라우저 창의 가로·세로 크기를 점진적으로 변경하면서 레이아웃이 정상적으로 반응하는지 확인한다.
- 최소 크기 제한, 고해상도 확대 제한, 텍스트 가독성, 요소 겹침, 콘텐츠 잘림 및 스크롤 발생 여부를 확인한다.
- Chrome, Edge, Firefox, Safari에서 주요 화면 및 반응형 동작을 검증한다.

## 핵심 개발 원칙

**FHD는 기본 설계 기준으로 사용하고, 고해상도에서는 화면 공간에 맞춰 UI가 적절하게 커지되 과도하게 확대되지 않아야 한다. 브라우저 창이 작아지면 요소도 유연하게 조정하되, 최소 크기 이하로 무조건 축소하지 않고 필요한 경우 배치를 변경하거나 스크롤을 허용해야 한다. 모바일과 태블릿은 별도로 최적화하며, 모든 주요 브라우저에서 일관된 화면과 동작을 제공해야 한다.**

## 프로젝트 적용 방식

루트 `.app-pages`와 페이지 최상위 `.app-page`가 공통 크기 기준을 공유한다. 운영체제의 배율·브라우저 확대에 따라 물리 해상도와 CSS 뷰포트는 다를 수 있으므로 실제 CSS 뷰포트의 가로·세로 공간을 기준으로 배치한다. 뷰포트에서 앱 헤더·푸터·툴바가 차지하는 공간을 제외해 본문 높이를 배분하며, 브라우저가 뷰포트에서 이미 제외한 주소창·탭 높이를 다시 빼지 않는다.

스크롤은 내용의 성격에 맞춰 관리한다. 긴 목록은 기존 번호 페이지네이션으로 표시량을 조절하고, 채팅은 메시지 영역 안에서 스크롤한다. FHD에서도 콘텐츠 양이나 구조상 필요한 페이지 스크롤은 허용한다. 표·게임판처럼 구조상 필요한 가로 스크롤은 해당 영역에 한정하고 페이지 전체의 불필요한 가로 넘침은 방지한다. 내용이나 버튼을 잘라내어 스크롤을 숨기지 않는다.

화면 전체를 `zoom`·`transform: scale()`로 확대·축소하지 않는다. 공통 변수와 rem/em, 제한된 유동 크기, 실제 가용 높이를 사용하되 요소별 특성과 최소·최대 크기를 우선한다. 브라우저 확대와 사용자가 지정한 글꼴 크기는 존중한다. 최소·최대 크기는 개념이며 CSS에서는 요소 특성에 따라 `min-width`·`min-height`·`max-width`·`max-height`·`clamp()` 등 실제 지원 속성과 함수를 사용한다.

## 현재 구현 수치

아래 표는 현재 공통 변수의 값이며 새 방향의 고정 목표값은 아니다. QHD·4K·5K에서 실제 콘텐츠 활용도와 가독성을 함께 검증한다.

기본 글꼴 16px과 브라우저 배율 100%에서의 기준이다. 실제 모니터 픽셀 수가 아닌 브라우저의 CSS 뷰포트를 사용한다.

| 항목 | FHD 1920px | QHD 2560px | 4K 3840px | 5K 5120px | 이후 상한 |
| --- | --- | --- | --- | --- | --- |
| 공통 글꼴 / rem | 16px | 18px | 22px | 24px | 기본값의 150% |
| 홈·일반·게임 본문 | 1440px | 1920px | 2475px | 2700px | 112.5rem |
| 관리자 본문 | 1600px | 약 2133px | 2750px | 3000px | 125rem |
| 인증 입력 카드 | 520px | 약 666px | 880px | 960px | 40rem |

`src/app/globals.css`가 수식을 한 곳에서 관리한다. 루트 글꼴은 120rem 이상에서 `clamp(100%, calc(62.5% + .3125vw), 150%)`로 증가한다. 본문은 일반 화면 75vw, 관리 화면 약 83.33vw를 활용하되 용도별 최소 기준과 최대 rem 상한을 적용한다. 좁은 화면에서는 부모 너비를 넘지 않는다. 기본 UI 글자는 1rem, 작은 화면은 .875rem이며 인증 입력은 1rem 이상을 유지한다. 기본 글꼴 설정과 브라우저 확대는 존중하며 `zoom`·`transform: scale()`로 페이지를 확대·축소하지 않는다.

화면 셸은 실제 가용 높이를 기준으로 헤더·본문·동작·푸터의 공간을 배분한다. 본문 내부의 짧은 카드는 내용 높이를 사용하며 불필요한 최소 높이나 여백으로 페이지를 늘리지 않는다. 표·목록은 현재 페이지의 표시량을 조정하고, 게임판과 채팅처럼 높이가 필요한 영역은 가용 높이와 용도별 상한을 함께 적용한다. 같은 행의 다른 요소도 이에 맞춰 조정한다. 기존 오목·테트리스의 고정 여유 높이와 크기 상한도 이 기준으로 검증하고 공통 변수에서 관리한다.

인증 화면은 입력 카드를 가로·세로 정중앙에 배치한다. 헤더는 위쪽 여백 행에 배치하고 카드 위·아래 행을 같은 비율로 나눠 헤더 높이가 중심을 밀어내지 않게 한다. 긴 가입 폼·작은 가로 화면·화상 키보드처럼 전체 내용이 창에 들어가지 않을 때에는 헤더와 입력을 가리지 않고 문서가 스크롤된다. 장식 삽화 때문에 폼 아래에 비대칭 여백을 추가하지 않는다.

## 적용과 검증

새 페이지는 다음 형태로 시작한다.

```tsx
export default function ExamplePage() {
  return <main className="app-page">내용</main>;
}
```

관리 화면은 `data-page-width="wide"`, 게임은 `data-page-width="game"`, 읽기용 안내는 `data-page-width="reading"`을 지정한다. CSS에서는 공통 gutter·gap·panel padding·title 변수를 재사용하고, rem/em 기반 크기를 활용하되 모든 요소에 같은 증가율을 강제하지 않고 용도별 최소·최대 크기와 고정·유동 크기를 조합한다. 무제한 vw 글꼴이나 큰 화면에서 다시 확대하는 별도 배율을 추가하지 않는다. 카드 열 수는 실제 남는 폭으로 결정한다.

검증은 FHD 최대화, 같은 모니터에서 브라우저의 폭·높이를 각각 줄인 상태, QHD·4K·5K, 모바일·태블릿의 가로·세로 방향에서 수행한다. 가로 넘침과 페이지 스크롤뿐 아니라 하단 동작·입력창의 노출, 내용 잘림, 카드·아바타·타이머의 크기 변화, 큰 화면의 활용도, 브라우저별 배치 차이를 함께 비교한다. 이 문서는 공통 개발 기준이며 문서 수정만으로 기존 화면 전체의 구현이 변경되지는 않는다.

Chrome·Edge·Firefox·Safari에서 같은 CSS 뷰포트와 배율을 사용해 결과를 비교하고, 폭·높이를 각각 점진적으로 변경해 중간 크기에서도 확인한다. 모바일·태블릿은 가로·세로 방향과 화상 키보드 표시 중 폼·메뉴·팝업·핵심 동작에 접근할 수 있는지도 검증한다. 기존 전역 Reset/Normalize와 공통 컨트롤을 재사용하고, 지원 차이가 있는 기능은 호환 가능한 방식이나 대체 스타일을 적용한다.

작업 결과에는 실제 확인한 브라우저·버전, CSS 뷰포트·배율, 확인 결과와 미검증 환경을 기록한다. 특정 브라우저나 해상도를 실행할 수 없다면 미검증으로 명시하며, 다른 브라우저 또는 뷰포트 에뮬레이션 결과만으로 전체 호환성이 확인되었다고 보고하지 않는다.

## 오목 대기실·대국 적용

데스크톱(너비 1101px 이상, 높이 600px 이상)은 셸에서 헤더·푸터의 실제 높이를 제외한 본문을 크기 컨테이너로 사용한다. 대기실은 프로필·규칙·준비/나가기·채팅 입력을 이 공간에 배분하고, 높이가 낮은 창에서는 프로필과 전적을 가로로 모은다. 연결 안내와 최대 길이 이름처럼 내용이 늘어나는 경우 본문 안에서 끝까지 접근할 수 있으며 푸터와 겹치거나 내용을 잘라내지 않는다.

대국의 A안 카드는 아바타·닉네임·돌·시계를 한 행에 모으고 아래에 얇은 시간 막대를 둔다. 판과 카드의 크기는 같은 본문 폭·높이를 참조하며 아바타·글자·여백은 카드의 em 단위를 공유한다. 연결 안내가 생기면 판의 높이를 먼저 양보한다. 태블릿에서는 카드를 판 위 두 열로, 작은 휴대폰에서는 한 열로 배치하고 채팅을 판 아래로 옮긴다. AI 대국도 같은 소형 카드와 좌표판 스타일을 공유하며 서버 시계·대국 상태는 크기 변경으로 초기화하지 않는다.
